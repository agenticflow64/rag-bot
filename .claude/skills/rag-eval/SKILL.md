# rag-eval: замер качества RAG-бота

Скилл для воспроизводимых замеров качества ответов бота.
Все цифры — из локальных замеров, всегда помечать «демо».

## Тестовый набор

~20 вопросов к документации, заложенной в базу:

- 14–16 вопросов, на которые в базе есть ответ (по темам инжеста:
  например, PostgreSQL — VACUUM, индексы, репликация; Spring Security —
  фильтры, CSRF, метод-секьюрити);
- 3–4 вопроса вне базы (то, чего в базе точно нет) — для замера доли отказов;
- для каждого вопроса с ответом заранее зафиксирован эталонный источник
  (файл + раздел).

Набор хранить в `data/eval-questions.local` (не в git), чтобы вопросы
не попали в промпты при разработке и не «подгонялись».

## Метрики

| Метрика | Определение |
|---|---|
| Hit rate источника | Доля ответов, где среди процитированных источников есть эталонный (или источник, содержащий тот же факт). |
| Latency, с | Время от вопроса до ответа; отдельно замерять retrieval-часть и полную (retrieval + генерация). |
| Доля отказов | Доля вне-базовых вопросов, на которые бот корректно ответил «нет ответа в базе» (из числа вне-базовых). Дополнительно: доля ложных отказов на вопросах с ответом. |

## Процедура прогона

1. Поднять `docker compose up`, прогнать ингест заново.
2. Прогнать все вопросы набора через бота программно (скрипт), не руками.
3. Для каждого ответа зафиксировать: цитированные источники, latency
   (retrieval и полная), был ли отказ.
4. Посчитать метрики; latency — медиана и p95.
5. Результат оформить таблицей и обновить раздел «Результат» в README
   (через `/case-update`).

## Формат результата

| Метрика | Значение | Комментарий |
|---|---|---|
| Hit rate источника | NN % | N из M вопросов |
| Latency полная (медиана / p95) | X с / Y с | retrieval + генерация |
| Latency retrieval (медиана) | X с | только поиск |
| Доля отказов (вне-базовые) | NN % | корректные «нет ответа в базе» |
| Ложные отказы | N шт. | вопросы с ответом, где бот отказал |

Под таблицей всегда строка: «Демо. Цифры из локальных замеров».
